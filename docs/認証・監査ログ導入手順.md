# 認証（AWS Cognito）・監査ログ 導入手順

OCR口座振替依頼書処理システムに、AWS Cognito によるログイン認証（BFF方式）と監査ログ機能を追加した際の、AWS設定手順とアプリケーション修正内容をまとめる。

---

## 1. 全体アーキテクチャ

```
[ブラウザ]
   │ ① 未認証でページアクセス
   ▼
[Next.js Middleware] ──未認証──▶ [/api/auth/login] ──▶ [Cognito Hosted UI ログイン画面]
   │ ② セッションCookieあり                                    │
   ▼                                                          │ ③ ログイン成功（認可コード）
[OCR画面]                                                      ▼
   │ ④ API呼び出し（httpOnly Cookieを自動送信）        [/api/auth/callback]
   ▼                                                    コード→トークン交換
[Nginx] ─▶ [FastAPI]                                    httpOnly Cookieに保存
              │ ⑤ get_current_user 依存（JWKSで署名/exp/aud/iss検証）
              │    request → AuthenticatedUser（email・groups）
              ▼
           [各ルーター] ─▶ ⑥ 監査ログ（AuditLogger）へ記録
```

### 認証方式
- **Cognito Hosted UI + Authorization Code Flow（PKCE付き）**
- **BFF方式**: トークンはすべて `httpOnly` / `Secure` Cookie に保存し、ブラウザのJavaScriptからは参照不可（XSS対策）。
- APIは Cognito が発行した JWT を検証する。将来 IdP を Entra ID に切り替えても、検証対象は常に「Cognito発行のJWT」のため、アプリ側の検証ロジックは変更不要。

### 権限管理（Cognito Group）
- `ocr-admin`: 管理者
- `ocr-user`: 一般利用者
- JWT内の `cognito:groups` クレームからロールを判定する。管理者専用APIは `require_groups()` 依存で保護できる。

## 2. AWS 設定手順

すべて **東京リージョン（ap-northeast-1）** で実施する。マネジメントコンソールでの手順を記載するが、CloudFormation/Terraform化も可能。

### 2-1. User Pool の作成

1. Cognito コンソール → 「ユーザープールを作成」
2. サインインオプション: **Eメール** を選択
3. パスワードポリシー・MFA: セキュリティ要件に合わせて設定（個人情報を扱うため MFA「必須」を推奨）
4. 自己サインアップ: **無効**（招待した3ユーザーのみを想定するため）
5. 必須属性: `email` を必須にする
6. プール名: 例 `ocr-user-pool`
7. 作成後、**User Pool ID**（例: `ap-northeast-1_xxxxxxxxx`）を控える

### 2-2. Hosted UI ドメインの設定

1. 対象User Pool → 「アプリケーションの統合」→「ドメイン」
2. Cognitoドメインを作成: 例 `ocr-auth`
   - 発行される値: `https://ocr-auth.auth.ap-northeast-1.amazoncognito.com`
3. このドメインを控える（`COGNITO_DOMAIN`）

### 2-3. アプリケーションクライアントの作成

1. 「アプリケーションの統合」→「アプリケーションクライアント」→「作成」
2. クライアントタイプ: **機密クライアント（Confidential）** を推奨
   - サーバー側（FastAPI）でトークン交換するため、クライアントシークレットを利用できる
   - シークレットを使わない場合は「パブリック」でも可（PKCEで保護）
3. 認証フロー: **Authorization code grant** を有効化
4. OpenID Connect スコープ: `openid` `email` `profile`
5. 許可されているコールバックURL:
   - 本番: `https://<本番ドメイン>/api/auth/callback`
   - 開発: `http://localhost:3000/api/auth/callback`
6. 許可されているサインアウトURL:
   - 本番: `https://<本番ドメイン>/`
   - 開発: `http://localhost:3000/`
7. 作成後、**Client ID** と（機密クライアントなら）**Client Secret** を控える

### 2-4. グループの作成

1. 対象User Pool →「グループ」→「グループを作成」
2. 以下2つを作成:
   - `ocr-admin`（管理者）
   - `ocr-user`（一般利用者）
3. 必要に応じて「優先順位（Precedence）」を設定（数値が小さいほど優先）

### 2-5. 初期ユーザーの登録

「ユーザー」→「ユーザーを作成」で以下3名を登録する。招待メール送信を有効にすると仮パスワードが通知される。

| メールアドレス | 割り当てグループ |
|---|---|
| takano-n@kiraboshi-system.co.jp | ocr-admin（または ocr-user） |
| ogawa-a@kiraboshi-system.co.jp | ocr-user |
| i-j@kiraboshi-system.co.jp | ocr-user |

- 作成後、各ユーザーの「グループ」タブから該当グループに追加する。
- 初回ログイン時にパスワード変更を求められる。

> CLIで一括登録する場合の例（値は環境に合わせて置換）:
> ```bash
> aws cognito-idp admin-create-user \
>   --user-pool-id ap-northeast-1_xxxxxxxxx \
>   --username takano-n@kiraboshi-system.co.jp \
>   --user-attributes Name=email,Value=takano-n@kiraboshi-system.co.jp Name=email_verified,Value=true \
>   --region ap-northeast-1
>
> aws cognito-idp admin-add-user-to-group \
>   --user-pool-id ap-northeast-1_xxxxxxxxx \
>   --username takano-n@kiraboshi-system.co.jp \
>   --group-name ocr-admin \
>   --region ap-northeast-1
> ```

## 3. 環境変数の設定

`.env`（`.env.example` をコピー）に以下を設定する。

```dotenv
# 認証
AUTH_ENABLED=true
COGNITO_USER_POOL_ID=ap-northeast-1_xxxxxxxxx
COGNITO_CLIENT_ID=<App Client ID>
COGNITO_CLIENT_SECRET=<機密クライアントの場合のみ>
COGNITO_REGION=ap-northeast-1
COGNITO_DOMAIN=https://ocr-auth.auth.ap-northeast-1.amazoncognito.com
COGNITO_REDIRECT_URI=https://<本番ドメイン>/api/auth/callback
COGNITO_LOGOUT_REDIRECT_URI=https://<本番ドメイン>/
COGNITO_GROUP_ADMIN=ocr-admin
COGNITO_GROUP_USER=ocr-user

# CORS（Cookie送信のためワイルドカード不可。実ドメインを指定）
ALLOWED_ORIGINS=https://<本番ドメイン>

# 監査ログ
AUDIT_LOG_DIR=/app/logs/audit
AUDIT_LOG_BACKEND=json
```

> ローカルで認証をバイパスしたい場合は `AUTH_ENABLED=false` にする。ダミーユーザー（`dev@example.com` / `ocr-admin`）で全APIが通り、Cognito未設定でも動作確認できる。

## 4. アプリケーション修正内容

### バックエンド（FastAPI）

| ファイル | 変更内容 |
|---|---|
| `backend/config.py` | Cognito設定・監査ログ設定を追加（環境変数から読み込み） |
| `backend/models/audit.py` | **新規**。監査イベント種別 `AuditEventType` と `AuditLog` スキーマ |
| `backend/services/audit_logger.py` | **新規**。抽象 `AuditLoggerBase` + JSON Lines実装 `JsonFileAuditLogger`。`log_event()` / `log_event_ctx()` ヘルパー |
| `backend/services/auth.py` | **新規**。JWKSキャッシュ、JWT検証 `verify_token()`、依存関数 `get_current_user` / `require_groups()` |
| `backend/routers/auth.py` | **新規**。`/api/auth/login` `/callback` `/logout` `/me`。トークン交換とhttpOnly Cookie発行 |
| `backend/routers/upload.py` | `get_current_user` 依存を追加。FILE_UPLOAD / OCR_EXECUTE を監査記録 |
| `backend/routers/batch.py` | 各エンドポイントに認証依存を追加。FILE_UPLOAD / OCR_EXECUTE / RESULT_DOWNLOAD を監査記録（バックグラウンド処理は `audit_ctx` で引き回し） |
| `backend/routers/result.py` | ルーター全体に認証依存を適用。CSV/PDFダウンロードを RESULT_DOWNLOAD として監査記録 |
| `backend/main.py` | auth ルーター登録。CORSを `ALLOWED_ORIGINS` ベースに変更（`allow_credentials=True` のためワイルドカード廃止） |
| `backend/requirements.txt` | `python-jose[cryptography]` を追加 |

### フロントエンド（Next.js）

| ファイル | 変更内容 |
|---|---|
| `frontend/middleware.ts` | **新規**。セッションCookieが無ければ `/api/auth/login` へリダイレクト |
| `frontend/lib/api.ts` | `authFetch`（`credentials: 'include'` + 401でログイン誘導）に全API呼び出しを移行。`getSession()` / `logout()` を追加 |
| `frontend/components/common/UserMenu.tsx` | **新規**。ログインユーザーのメール・ロール表示とログアウトボタン |
| `frontend/app/layout.tsx` | ヘッダーに `UserMenu` を配置 |

### インフラ

- `nginx/nginx.conf`: 既存の `location /api/` で `/api/auth/*` も backend へプロキシされるため変更不要。`X-Forwarded-For` 設定済みで監査ログのIP取得に対応。
- `docker-compose.yml`: backend が `app-logs:/app/logs` をマウント済みのため、監査ログ（`/app/logs/audit`）は既存ボリュームに永続化される。変更不要。

## 5. 認証・認可の要件対応

| 要件 | 対応 |
|---|---|
| 1. 未認証ならログイン画面へ遷移 | `middleware.ts` がCookie未所持を検知し Hosted UI へ誘導 |
| 2. 認証成功者のみOCR画面へ | Cookie保持者のみページ通過。API側でもJWT検証 |
| 3. FastAPI APIのJWT検証 | `get_current_user` 依存で全業務APIを保護（署名/exp/aud/iss検証） |
| 4. ログインユーザーのメール確認 | `/api/auth/me` およびヘッダーの `UserMenu` で表示 |
| 5. 将来のEntra ID SSO連携 | Cognitoをフェデレーションハブとして利用。IdP追加時もアプリの検証ロジックは不変 |
| 6. AWS設定手順・アプリ修正提案 | 本ドキュメント |

## 6. 監査ログ

### 記録イベント
`login_success` / `login_failure` / `logout` / `file_upload` / `ocr_execute` / `result_download`

### 記録項目（要件対応）
| 項目 | フィールド |
|---|---|
| 実行日時 | `timestamp`（UTC ISO8601） |
| ユーザーメール | `user_email` |
| 実行操作 | `event_type` |
| 対象ファイル名 | `target_file` |
| 接続元IP | `ip_address`（Nginxの `X-Forwarded-For` から取得） |

補助項目: `result`（成功/失敗）、`user_groups`、`user_agent`、`detail`

### 出力形式・保存先
- JSON Lines（1イベント1行）。`audit-YYYYMMDD.log` として日付別に出力。
- 保存先: `AUDIT_LOG_DIR`（既定 `/app/logs/audit`、`app-logs` ボリューム配下）。

### 出力例
```json
{"timestamp":"2026-09-02T03:41:34.364167Z","event_type":"login_success","result":"success","user_email":"takano-n@kiraboshi-system.co.jp","user_groups":["ocr-admin"],"target_file":null,"ip_address":"203.0.113.10","user_agent":"Mozilla/5.0 ...","detail":null}
```

### 将来拡張
`AuditLoggerBase` を継承した実装を追加し、`AUDIT_LOG_BACKEND` を切り替えるだけで保存先を変更できる。
- `s3`: S3へ逐次/バッチアップロード
- `cloudwatch`: CloudWatch Logs へ送信
- `dynamodb`: 検索性重視でDynamoDBへ保存

呼び出し側（ルーター）は `log_event()` を使うだけのため、保存先変更の影響を受けない。

## 7. 将来: Microsoft Entra ID との SSO 連携手順（概要）

Cognitoを変更せずアプリ側の改修も最小で連携できる。

1. Entra ID（Azure ポータル）でアプリ登録を作成し、OIDCの発行者URL・クライアントID/シークレット、リダイレクトURI（CognitoのIdPレスポンスURL）を取得。
2. Cognito User Pool →「サインインエクスペリエンス」→「フェデレーティッドIDプロバイダー」→ OIDC（または SAML）で Entra ID を追加。
3. 属性マッピング: Entra IDの `email` を Cognitoの `email` にマッピング。
4. App Client の「IDプロバイダー」で Entra ID を有効化。
5. グループ連携が必要な場合は、Entra IDのロール/グループ → Cognitoグループへのマッピング、または Pre Token Generation Lambda で `cognito:groups` を付与。

アプリ側は Hosted UI のログイン画面に「Entra IDでサインイン」ボタンが増えるだけで、`/api/auth/*` とJWT検証コードは変更不要。

## 8. 動作確認

### ローカル（認証バイパス）
```bash
# backend: AUTH_ENABLED=false で起動 → /api/* がダミーユーザーで通る
```

### 本番相当（認証有効）
1. `.env` にCognito設定を投入し `docker compose up -d`
2. ブラウザで本番URLにアクセス → Hosted UI へリダイレクトされる
3. 登録ユーザーでログイン → OCR画面が表示され、ヘッダーにメールが出る
4. PDFアップロード・OCR・ダウンロードを実行
5. `docker compose exec backend cat /app/logs/audit/audit-<日付>.log` で監査ログを確認
6. ログアウト → Cookieが破棄され、再アクセスで再びログインを要求される

### 実施済みの自動検証（本実装時）
- `GET /api/auth/me`（Cookieなし）→ 401
- `GET /api/auth/login` → 302（Hosted UIへPKCE付きリダイレクト）
- `POST /api/upload`（未認証）→ 401
- 監査ログのJSON Lines出力（login_success / file_upload）を確認
